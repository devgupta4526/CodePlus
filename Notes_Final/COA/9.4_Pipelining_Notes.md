## 1️⃣ Pipelining Basics

### 🏭 1.1 Concept of Pipelining — Assembly-Line Analogy
- **Pipelining** is a technique where multiple instructions are **overlapped in execution** — while one instruction is being decoded, another can be fetched, and so on — similar to a **car assembly line** where different stations work on different cars simultaneously.
- 🚗 **Analogy**: Imagine a car wash with 4 stages — *Wash → Rinse → Wax → Dry*. Without pipelining, one car goes through all 4 stages before the next car even starts. With pipelining, as soon as Car 1 moves from Wash to Rinse, Car 2 can enter Wash — all stations stay busy, dramatically increasing throughput (cars/hour), even though a **single car** still takes the same total time to finish.

```
        ⏱️  WITHOUT PIPELINING (Sequential)
   Car1: [Wash][Rinse][Wax][Dry]
   Car2:                          [Wash][Rinse][Wax][Dry]
   Car3:                                                   [Wash][Rinse][Wax][Dry]

        ⚡ WITH PIPELINING (Overlapped)
   Car1: [Wash][Rinse][Wax][Dry]
   Car2:        [Wash][Rinse][Wax][Dry]
   Car3:               [Wash][Rinse][Wax][Dry]
```
> 🟢 Key Insight: Pipelining improves **throughput** (instructions completed per unit time), NOT the **latency** of a single instruction.

### 🔄 1.2 Uniprocessing vs Multiprocessing
| Feature | 🟦 Uniprocessing | 🟧 Multiprocessing |
|---|---|---|
| Number of processors | One CPU | Two or more CPUs |
| Execution | Sequential (or pipelined within 1 CPU) | Truly parallel across multiple CPUs |
| Complexity | Lower | Higher (needs synchronization, coherence) |
| Throughput | Limited by single CPU speed | Scales with number of processors (ideally) |
| Example | Classic single-core pipelined CPU | Modern multicore servers |

### 🏛️ 1.3 IBM 801 — Historical RISC Pipelining Example
- The **IBM 801** (1970s, John Cocke) is regarded as the **first RISC (Reduced Instruction Set Computer)** design.
- It demonstrated that a **simple, reduced instruction set with a fixed instruction format** enables efficient pipelining — since every instruction takes a predictable, uniform path through pipeline stages.
- This philosophy directly influenced modern RISC architectures (MIPS, ARM, RISC-V), which are all designed with pipelining efficiency as a first-class goal.

### 🪜 1.4 Basic 5-Stage Pipeline (IF → ID → EX → MEM → WB)
```
┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐
│  IF  │──►│  ID  │──►│  EX  │──►│ MEM  │──►│  WB  │
└──────┘   └──────┘   └──────┘   └──────┘   └──────┘
 Fetch      Decode      Execute    Memory     Write
                                    Access     Back
```
| Stage | Full Form | What Happens |
|---|---|---|
| 🔵 **IF** | Instruction Fetch | Instruction is fetched from memory using the address in PC; PC incremented |
| 🟢 **ID** | Instruction Decode | Opcode is decoded, operands/registers are read from the register file |
| 🟡 **EX** | Execute | ALU performs the arithmetic/logic operation (or computes memory address) |
| 🟠 **MEM** | Memory Access | Memory is read (LOAD) or written (STORE) if the instruction requires it |
| 🔴 **WB** | Write Back | Result is written back into the destination register |

### 📊 Pipeline Execution Diagram (No Hazards)
| Instr \ Cycle | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| I1 | IF | ID | EX | MEM | WB |  |  |  |
| I2 |  | IF | ID | EX | MEM | WB |  |  |
| I3 |  |  | IF | ID | EX | MEM | WB |  |
| I4 |  |  |  | IF | ID | EX | MEM | WB |

> ✅ With an ideal 5-stage pipeline and no hazards, one instruction **completes every clock cycle** after the pipeline fills up.

> ### ⚠️ Common Traps & Exam Tips
> - 🔑 Pipelining improves **throughput**, not the execution time of a SINGLE instruction (a single instruction still takes 5 cycles to fully complete — latency is unchanged or even slightly worse due to pipeline overhead).
> - 🔑 IBM 801 is tested as the "**first RISC machine**" — a common historical MCQ fact.
> - 🔑 Don't confuse **Uniprocessing with pipelining** — a single pipelined CPU is still "uniprocessing" (one CPU), just internally overlapping instruction stages; true multiprocessing needs multiple physical CPUs.

## 2️⃣ Performance & Speedup

### 📐 2.1 Speedup Formula — Derivation
Without pipelining, `n` instructions each taking `k` cycles (for a `k`-stage pipeline) run **sequentially**:
```
Time (Non-Pipelined) = n × k cycles
```
With pipelining, the pipeline **fills up** in `k` cycles for the first instruction, then completes **one instruction per cycle** thereafter:
```
Time (Pipelined) = k + (n − 1) cycles
```
> 📦 **Formula Box — Speedup**
> ```
> Speedup (S) = Time(Non-Pipelined) / Time(Pipelined)
>             = (n × k) / (k + (n − 1))
> ```
> **As n → ∞ (very large number of instructions):**
> ```
> Maximum Speedup → k   (equal to the number of pipeline stages)
> ```

### 🟢 2.2 Ideal CPI = 1 Case
- In an **ideal pipeline** (no hazards, no stalls), exactly **one instruction completes per clock cycle** after the pipeline is full → **CPI (Cycles Per Instruction) = 1**.
- This is the theoretical best case; real pipelines have CPI slightly **greater than 1** due to hazards/stalls.

### 📈 2.3 Throughput and Efficiency Formulas
> 📦 **Formula Box**
> ```
> Throughput = Number of Instructions Completed / Total Time Taken
>
> Efficiency = Speedup Achieved / Number of Pipeline Stages (k)
>            = Actual Speedup / Maximum Possible Speedup
> ```

### 🚧 2.4 Problems That Reduce Ideal Pipelining Performance
- **Hazards** (Structural, Data, Control) — force stalls/bubbles, breaking the "1 instruction per cycle" ideal.
- **Unequal stage delays** — pipeline clock must be set by the SLOWEST stage, wasting time in faster stages.
- **Pipeline fill/drain overhead** — the initial fill time (`k` cycles) and any drain time are "wasted" relative to steady-state throughput, especially significant for SHORT instruction sequences.

### 📝 Solved Numericals

**Q1.** A 5-stage pipeline executes 100 instructions with no hazards. Find the speedup over non-pipelined execution.
> **Solution**:
> Non-Pipelined Time = 100 × 5 = 500 cycles
> Pipelined Time = 5 + (100 − 1) = 104 cycles
> Speedup = 500 / 104 ≈ **4.81**

**Q2.** For an infinitely long instruction stream on a 4-stage pipeline, find the maximum theoretical speedup.
> **Solution**: Maximum Speedup = k = **4** (as n → ∞)

**Q3.** A pipeline has 6 stages, each taking 20 ns. Find the time to execute 50 instructions using pipelining.
> **Solution**:
> Pipelined Time = k + (n−1) cycles = 6 + 49 = 55 cycles
> Total Time = 55 × 20 ns = **1100 ns**

**Q4.** For Q3, find the non-pipelined execution time and the resulting speedup.
> **Solution**:
> Non-Pipelined Time = n × k × (cycle time) = 50 × 6 × 20 = 6000 ns
> Speedup = 6000 / 1100 ≈ **5.45**

**Q5.** A pipeline achieves a speedup of 3.5 with 5 stages. Find the efficiency.
> **Solution**: Efficiency = Speedup / k = 3.5 / 5 = **0.7 (70%)**

**Q6.** A non-ideal pipeline has an average CPI of 1.4 (due to hazards) instead of the ideal CPI = 1, running at a clock rate of 2 GHz, for a 1000-instruction program. Find the actual execution time.
> **Solution**:
> Total Cycles = CPI × Instructions = 1.4 × 1000 = 1400 cycles
> Execution Time = 1400 / (2×10⁹) = **700 ns (0.7 μs)**

> ### ⚠️ Common Traps & Exam Tips
> - 🔑 The formula `Time(Pipelined) = k + (n−1)` is the SINGLE most important pipelining formula — memorize the derivation, not just the result.
> - 🔑 Maximum Speedup equals the **number of stages (k)**, achieved only in the theoretical limit of infinite instructions — for finite `n`, actual speedup is always LESS than `k`.
> - 🔑 Efficiency is a **fraction between 0 and 1** (or 0–100%) — if your calculated efficiency exceeds 1, you've made an arithmetic error.

## 3️⃣ Structural & Control Hazards

### 🧱 3.1 Structural Hazard — Definition & Example
- **Structural Hazard**: Occurs when **two or more instructions need the SAME hardware resource** at the same clock cycle (resource conflict).
- **Example**: If instruction and data share a **single memory** (Von Neumann style), an instruction in the **MEM** stage (accessing data) and another instruction in the **IF** stage (fetching the next instruction) may both need memory access **simultaneously** — causing a conflict.

```
Instr \ Cycle    1    2    3    4    5
I1 (LOAD)       IF   ID   EX   MEM  WB
I2              --   IF   ID   EX   MEM  ← wants IF while I1 wants MEM (cycle 4) — CONFLICT if single memory port
```
> 🛠️ **Solution**: Use **separate instruction and data memories/caches** (Harvard-style organization) to avoid resource contention.

### 🚦 3.2 Control Hazard — Definition & Example
- **Control Hazard**: Occurs due to **branch instructions** — the pipeline doesn't know WHICH instruction to fetch next until the branch is resolved (evaluated), potentially fetching the WRONG instructions.
- **Example**:
```
I1: BEQ R1, R2, LABEL     ; branch instruction
I2: ADD R3, R4, R5        ; fetched next by default — but might be WRONG if branch is taken!
```
If the branch is taken, I2 (and possibly I3) were **wrongly fetched** and must be discarded (flushed), wasting cycles.

### 🛠️ 3.3 Solutions to Control Hazards
| Technique | Description |
|---|---|
| 🔮 **Branch Prediction** | Hardware GUESSES the branch outcome (taken/not-taken) in advance and speculatively fetches accordingly; if wrong, pipeline is flushed and restarted (misprediction penalty) |
| ⏳ **Delayed Branching** | Compiler places a useful, branch-independent instruction in the "delay slot" right after the branch — this instruction executes regardless of the branch outcome, so no cycles are wasted |
| 🎯 **Branch Target Buffer (BTB)** | A small cache that stores previously computed branch target addresses, allowing the CPU to quickly fetch from the predicted target BEFORE the branch is fully decoded/resolved |

> ### ⚠️ Common Traps & Exam Tips
> - 🔑 Structural hazards are solved via **hardware duplication** (e.g., separate memories, extra ALUs) — a hardware-level fix; NOT solvable by software/compiler alone.
> - 🔑 Delayed branching is a **compiler-level (software) technique**, while branch prediction/BTB are **hardware-level techniques** — a frequent classification trap.
> - 🔑 Control hazards specifically arise from **branch/jump instructions** — don't confuse with data hazards (which arise from data dependency between instructions, not control flow).

## 4️⃣ Data Hazards & Solutions

### 🔗 4.1 RAW, WAR, WAW Hazards

| Hazard | Full Form | Condition | Example |
|---|---|---|---|
| 🔴 **RAW** | Read After Write | An instruction tries to READ a register BEFORE a previous instruction has WRITTEN to it | `I1: ADD R1, R2, R3` <br> `I2: SUB R4, R1, R5` (I2 reads R1 before I1 writes it) |
| 🟡 **WAR** | Write After Read | An instruction tries to WRITE a register BEFORE a previous instruction has READ the old value | `I1: ADD R4, R1, R2` <br> `I2: SUB R1, R3, R5` (I2 writes R1 before I1 reads old R1) — occurs mainly with out-of-order execution |
| 🟢 **WAW** | Write After Write | Two instructions WRITE to the same register, and must complete in the correct final order | `I1: ADD R1, R2, R3` <br> `I2: SUB R1, R4, R5` (both write R1 — final value must reflect I2, the later instruction) |

> 🟢 **RAW is the MOST common and problematic hazard** in simple in-order pipelines (also called a "true dependency"); WAR and WAW ("false/name dependencies") mainly matter in out-of-order/superscalar pipelines.

### 🛠️ 4.2 Solutions to Data Hazards
| Technique | Description |
|---|---|
| ⚡ **Forwarding / Bypassing** | The ALU result is "forwarded" directly from the EX/MEM stage output back to the EX stage input of a dependent instruction, WITHOUT waiting for it to be written back to the register file first |
| ⏸️ **Stalling (Pipeline Bubble)** | The pipeline is deliberately paused (inserting "bubble"/NOP cycles) until the dependency is resolved, when forwarding alone isn't sufficient (e.g., LOAD-USE hazard) |
| 🔀 **Compiler-Based Reordering** | The compiler rearranges independent instructions to be placed BETWEEN dependent ones, hiding the hazard latency without hardware stalls |

### 📊 Pipeline Diagram — RAW Hazard with Stalling (No Forwarding)
```
I1: ADD R1, R2, R3
I2: SUB R4, R1, R5    ← depends on R1 from I1

Cycle:           1    2    3    4    5    6    7
I1 (ADD)        IF   ID   EX   MEM  WB
I2 (SUB)             IF   ID*  ID*  ID   EX   MEM   WB
                            (stall) (stall)  — waits for R1 to be written back in cycle 5
```
*(Without forwarding, I2 must stall until I1's WB stage completes, in cycle 5, before I2 can read the correct R1 value in ID.)*

### 📊 Pipeline Diagram — Same Hazard WITH Forwarding
```
Cycle:           1    2    3    4    5
I1 (ADD)        IF   ID   EX   MEM  WB
I2 (SUB)             IF   ID   EX   MEM  WB
                              ↑
                    Forwarded directly from I1's EX/MEM output into I2's EX stage input
                    (no stall needed!)
```

### 📝 Solved Numerical (Mirrors GATE 2010-style)

**Q.** Consider the following instruction sequence on a 5-stage pipeline (IF, ID, EX, MEM, WB) with **full forwarding** implemented (EX/MEM and MEM/WB → EX), EXCEPT that a **LOAD-USE hazard** (a register loaded from memory, immediately used by the NEXT instruction) still requires **1 stall cycle** (since the loaded value isn't available until after MEM stage):
```
I1: LOAD R1, 0(R2)
I2: ADD  R3, R1, R4     ← uses R1 immediately after LOAD
I3: SUB  R5, R6, R7
```
Find the total number of cycles to complete all 3 instructions.

> **Solution**:
> - I1 (LOAD): IF(1) ID(2) EX(3) MEM(4) WB(5)
> - I2 (ADD) needs R1, but R1 is only available after I1's MEM stage (cycle 4) — with forwarding from MEM/WB, I2's EX stage must occur in cycle 5 or later → **1 stall cycle required** for I2.
>   I2: IF(2) ID(3) [stall](4) EX(5) MEM(6) WB(7)
> - I3 (SUB), independent, follows right behind I2 (also delayed by the stall):
>   I3: IF(3) [stall](4) ID(5) EX(6) MEM(7) WB(8)
>
> **Total cycles = 8** (compared to the hazard-free ideal of `k + (n−1) = 5 + 2 = 7` cycles) → **1 extra cycle lost due to the LOAD-USE hazard stall.**

### ⚖️ 4.3 Comparison of All Three Hazard Types
| Hazard Type | Definition | Example Cause | Typical Solution(s) |
|---|---|---|---|
| 🧱 **Structural** | Two instructions need the SAME hardware resource simultaneously | Shared memory port for instruction fetch & data access | Separate instruction/data memory (Harvard), duplicate hardware units |
| 🔗 **Data** | An instruction depends on the result of a prior instruction not yet available (RAW/WAR/WAW) | `ADD R1,..` followed immediately by `SUB ..,R1,..` | Forwarding/bypassing, stalling, compiler reordering |
| 🚦 **Control** | Next instruction to fetch is uncertain due to a branch/jump | `BEQ` followed by sequential instructions that may be wrong | Branch prediction, delayed branching, branch target buffer |

> ### ⚠️ Common Traps & Exam Tips
> - 🔑 **RAW = "true dependency"** — cannot be eliminated by reordering alone, only mitigated via forwarding/stalling; **WAR/WAW = "false dependency"** — can often be eliminated entirely via register renaming.
> - 🔑 **LOAD-USE hazard** is a classic case where even FULL forwarding cannot avoid at least **1 stall cycle**, because the data simply isn't ready until after the MEM stage — a favorite GATE numerical trap.
> - 🔑 Forwarding solves MOST data hazards without stalling, but NOT all — always check if the producing instruction's result is available in time for the consuming instruction's EX stage.

## 5️⃣ Vector Processing Unit

### 🎯 5.1 Need for Vector Processing
- Scalar processors operate on **one data element at a time** — inefficient for applications involving large, uniform data sets (scientific computing, graphics, matrix operations) where the SAME operation must be applied repeatedly across many elements.
- **Vector Processing** allows a SINGLE instruction to operate on an ENTIRE array (vector) of data elements, dramatically improving throughput for such data-parallel workloads — a hardware realization of the **SIMD** concept (recall Flynn's Taxonomy from Chapter 9.1).

### 🏗️ 5.2 Vector Processor Architecture
```
                 ┌───────────────────────────┐
                 │      Vector Registers        │
                 │  V1: [a1][a2][a3]...[an]      │
                 │  V2: [b1][b2][b3]...[bn]      │
                 └──────────────┬────────────────┘
                                 ▼
                 ┌───────────────────────────┐
                 │   Pipelined Functional Unit  │
                 │   (e.g., Vector Adder)        │
                 └──────────────┬────────────────┘
                                 ▼
                 ┌───────────────────────────┐
                 │  Result Vector Register      │
                 │  V3: [a1+b1][a2+b2]...[an+bn] │
                 └───────────────────────────┘
```
- **Vector Registers**: Hold entire arrays of data (not just a single scalar value).
- **Pipelined Functional Units**: The ALU itself is pipelined internally, so once the pipeline fills, one result (e.g., one element sum) emerges per cycle.

### 🔁 5.3 How Vector Processing Works (Pipelined Vector Operations)
- A single vector instruction (e.g., `VADD V3, V1, V2`) is broken down internally into a **pipeline of per-element operations**.
- Because the functional unit is deeply pipelined, elements are fed in one after another — while element 1 is in the "multiply" stage, element 2 can already be in "fetch," and so on — achieving very high throughput for the entire vector operation.

### 🏷️ 5.4 Types of Vector Processing
| Type | Description |
|---|---|
| 🟦 **Memory-to-Memory** | Vector operands are read directly from MEMORY and results are written directly back to MEMORY (no intermediate vector registers) — simpler but slower due to memory bandwidth limits |
| 🟧 **Register-to-Register** | Vector operands are first loaded into VECTOR REGISTERS, operated on, and results stored back into vector registers (memory accessed only for bulk load/store) — faster, more common in modern vector processors |

### 🛣️ 5.5 Lanes in Vector Processors
- A **lane** is a hardware "channel" containing a full set of functional units (ALU, etc.) capable of processing ONE vector element independently.
- Multiple lanes allow a vector processor to work on **several elements of the vector SIMULTANEOUSLY** (true parallelism), not just pipelined sequential elements — e.g., a processor with **4 lanes** can process 4 vector elements per cycle instead of just 1.
```
              Lane 1     Lane 2     Lane 3     Lane 4
V1:          [a1]       [a2]       [a3]       [a4]     ┐
V2:          [b1]       [b2]       [b3]       [b4]     ├─► All 4 additions
                ▼           ▼          ▼          ▼      happen in PARALLEL
V3:          [a1+b1]    [a2+b2]    [a3+b3]    [a4+b4]  ┘  (same cycle!)
```
> 🟢 More lanes = more elements processed per cycle = higher throughput (at the cost of more hardware/area).

> ### ⚠️ Common Traps & Exam Tips
> - 🔑 Vector processing is the hardware embodiment of **SIMD** from Flynn's Taxonomy — a common cross-chapter linking question.
> - 🔑 **Register-to-Register** vector processors are generally FASTER than **Memory-to-Memory** ones (avoid repeated memory bandwidth bottlenecks) — a frequently tested comparison.
> - 🔑 Don't confuse **pipelining within a lane** (sequential elements processed with overlap, one per cycle after fill) with **multiple lanes** (truly parallel/simultaneous processing of DIFFERENT elements in the SAME cycle) — these are two independent mechanisms for speeding up vector operations, and can be combined.

### 🎯 Key Conceptual Recap
- **Pipelining** overlaps instruction execution stages (IF-ID-EX-MEM-WB) to boost **throughput**, not single-instruction latency. IBM 801 = first RISC, pioneer of pipelining-friendly design.
- **Speedup** approaches the number of stages `k` as instruction count `n → ∞`; real speedup is always less due to fill/drain overhead and hazards.
- **3 Hazard Types**: 🧱 Structural (resource conflict → duplicate hardware), 🔗 Data (RAW/WAR/WAW → forwarding/stalling/reordering), 🚦 Control (branches → prediction/delayed branching/BTB).
- **RAW** = true dependency (unavoidable, needs forwarding/stall); **WAR/WAW** = false dependency (fixable via renaming).
- **LOAD-USE hazard**: even with full forwarding, at least 1 stall cycle is unavoidable — classic GATE numerical trap.
- **Vector Processing**: SIMD in hardware form; Register-to-Register faster than Memory-to-Memory; **Lanes** = parallel hardware channels (true simultaneous element processing), distinct from pipelining (overlapped sequential processing).
